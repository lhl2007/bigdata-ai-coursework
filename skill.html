Skill 智能体技能 —— 课程作业笔记

大数据与人工智能课程作业个人理解 · 仅代表本人当前认知，欢迎指正

Skill（技能） 是预先打包好的任务知识包，可以理解为 Agent 的"插件"。 当 Agent 遇到特定类型任务时，把对应的 Skill 加载进上下文，模型就临时学会了如何按这套 SOP 干活； 任务结束，Skill 又可以被卸载，下次再用。

课程上一句话定义我印象很深： "Skill 不是给模型看的，是给使用模型的人的——它帮你把经验沉淀下来，让模型下次直接复用。"

一、Skill 的定义与最小形态

一个 Skill 通常是一个目录（或一个对象），至少包含：

  • SKILL.md：描述这个 Skill 是干什么的、什么时候用、怎么用、有什么已知坑
  • references/：详细参考资料、领域知识、规范、API 文档
  • assets/（可选）：模板文件、图片、示例输入输出
  • scripts/（可选）：校验脚本、辅助小工具

而最最小形态可以只是一段提示词："让模型写 SQL 时，先用 EXPLAIN 看执行计划， 再考虑是否建索引"——这就是一个 micro-skill。

课程上老师提的判断口径："如果同一套任务知识我们说过三遍，就该提成 Skill。" 这条非常工程化，比"看上去像 Skill"实在得多。

二、Skill 的"插件"定位

把 Skill 想象成 Agent 的"插件"很贴切，几点对得上：

对比项浏览器插件Skill（Agent 技能）
存在形式 一份独立的扩展包 一份独立的目录或对象
激活方式 按需启用 / 关闭 按需加载进上下文 / 卸载
对宿主的影响 不影响其它扩展 只在加载期间占用上下文，不污染默认行为
复用范围 同一浏览器全局可用 被多个 Agent / 多个项目共享
版本管理 可升级、可回滚 同样可升级、可回滚

"插件"这个比喻的关键是解耦：Agent 本身不内置所有业务知识， 而是把知识外挂成 Skill，主程序反而更轻、更通用。

三、Skill 的三大作用

① 能力扩展 Extensibility

Agent 不需要每次都重新训练——加载新 Skill 就能"会"新任务。

  • 想做数据分析？加载 data-analysis-skill
  • 想做 SQL 优化？加载 sql-tuning-skill
  • 想做代码评审？加载 code-review-skill

这是用 Skill 替代 fine-tuning的常见工程模式——快得多、可逆得多。

课程上有个数据我记住了：把一个新 SOP 沉淀到 Skill 里大约 1~2 小时； 同样的事情如果用模型微调要 1~2 周还要 GPU。这就解释了"为什么我们都在写 Skill"。

② 标准化调用 Standardized Interface

Skill 强制团队用同一套输入输出、同一种最佳实践。这意味着：

  • 不同人写的 Agent，行为可预期，协作成本低
  • 模型换了一家厂商，Skill 的接口不变，业务连续性保住了
  • 新人接手项目，按 Skill 跑就行，不用从零摸索

课程里举了反面例子：组里 6 个人各自维护一份"怎么写 commit message"的口头规范， 6 个月后仓库里有 6 种风格。引入 commit-message-skill 后第二天就一致了。

③ 多 Agent 复用 Reusability

同一份 Skill 可以被多个 Agent 共享，沉淀一次、到处跑。

使用场景说明
单 Agent 多 Skill 一个通用 Agent，加载不同 Skill 就能切换任务类型
多 Agent 共用 Skill 团队里的不同 Agent（数据 Bot、客服 Bot、运维 Bot）共享同一份领域 Skill
跨项目复用 公司级"代码审查 Skill"在不同项目仓库里复用
跨模型复用 同一 Skill 在不同底层模型（GPT、Claude、本地开源）下都生效

四、Skill 的生命周期

编写 Skill
（沉淀经验 / 规范）
注册到 Skill 库
（带元数据）
Agent 需要时按需加载
拼入当前上下文
任务结束 / 卸载
用后评估 → 优化更新

关键在最后两步：用后评估 + 持续维护。一个 Skill 写好后如果没人更新， 模型升级或工具变更后它就会失效。课程作业里推荐把每个 Skill 配一份"Skill 评测用例"， 类似单元测试，每次模型更新就跑一遍。

五、真实应用场景（课程作业里能举的例子）

场景用到的 Skill价值
团队代码助手统一规范 code-review-skill / commit-message-skill PR 风格统一，模型换厂商也不变
数据分析师 Bot data-analysis-skill / sql-tuning-skill 新人 30 分钟上手出报表

六、容易混淆的点 / 使用边界

易混说法我目前的理解
"Skill = 一段 Prompt" 最小形态是 Prompt，但工程形态含 SKILL.md / references / 评测用例
"Skill 越多 Agent 越强" 不是。每多加载一个 Skill 就多吃一截上下文，且 Skill 之间可能冲突
"Skill 一旦写好就万能" 需要维护。模型升级、工具变更、流程调整时 Skill 可能失效
"Skill 可以替代 fine-tuning" 大部分业务可以，少量深度领域知识还是得训练
"Skill 必须人来写" 可以由 Agent 自己从历史对话里总结经验、提炼成 Skill（meta-skill 思路）

七、和 Agent / 上下文的关系（呼应其它笔记）

  • Skill 是抽屉里的 SOP，不运行时只占存储，不占上下文
  • Agent 决定何时加载哪个 Skill——这也是一种规划能力
  • 加载 Skill 的行为就是把 SOP 临时写进上下文，所以 Skill 受限于上下文窗口
  • Skill 本身不该写"业务数据"，只写"怎么干活"；数据走 RAG

LLM 上下文 Context —— 课程作业笔记

大数据与人工智能课程作业个人理解 · 仅代表本人当前认知，欢迎指正

大模型上下文（Context） 指大模型在这一次请求里能"看见"的全部信息—— 系统提示、对话历史、用户当下的提问、工具调用的返回值、未来得及丢掉的草稿……全在里面。 模型推理时只看见这一坨，看不见这块之外的任何东西。

课程上反复强调：很多人误以为模型"什么都记得"，其实是上下文假装让它记得。 上下文怎么管理、怎么扩张，几乎决定了 Agent 与大模型应用的全部表现。

一、上下文窗口是什么

"上下文窗口（Context Window）"就是模型一次请求最多能吃下的 token 总数上限—— 不只是用户的提问，是系统提示 + 历史对话 + 工具返回值 + 用户提问 + 输出预留加起来。

常见模型上下文窗口量级备注
早期 GPT-3 / 多数开源 7B 模型 2K ~ 4K token 聊几轮就开始忘事
GPT-3.5 / GPT-4 早期 8K ~ 32K 可以做长文档摘要
主流大模型 2024~2025 128K ~ 1M 看上去很大，但实际有效长度往往远小于官方数字
课程上一个常见陷阱：模型的"上下文窗口"和"上下文能用好"是两件事。 厂商标称 128K，但跑到 80K 后准确率已经断崖式下降——这就是后面要讲的"截断遗忘"和"中间信息丢失"。

二、截断遗忘现象：上下文满了会怎样

模型本身不会"内存"溢出，框架/SDK 通常有三种截断策略：

  • 头部截断：保留最近的 N 轮，丢掉最老的（早期对话完全丢失）
  • 尾部截断：保留系统提示+早期，丢掉最近（用户当前的问题被吃掉了）
  • 中间截断：保留首尾，把中间一段挤掉（看似保留多，但中间关键对话/工具结果最容易丢）

"中间信息丢失"现象（Lost-in-the-Middle）

论文与课程都明确指出：把关键信息放在上下文的开头或结尾，模型更容易找到； 放在正中间反而容易被忽略。这与人类"首因效应/近因效应"很像。

  • 长文档 RAG 问答：把检索片段放在 用户问题之前 比放在之后效果更好
  • Agent 工具调用：把最近一次工具返回值紧贴当前提问拼接，避免被中间隔开
  • 系统提示：尽量放最前，且单独成段，模型会把它当"宪法"读
课程作业里的真实坑：有同学用长上下文做课程笔记问答，把笔记放最前面、问题放最后， 答案准确率比"问题在最前、笔记在后"高一截——亲身验证了 Lost-in-the-Middle。

三、算力开销：长上下文不是免费的

上下文长度直接影响显存占用和推理时延，且是非线性关系：

影响维度短上下文长上下文代价
自注意力计算 O(n²) 但 n 小，几乎无感 n=1M 时算力/显存爆炸增长 长输入推理延迟显著上升
KV Cache 显存 几乎不占 每一个新增 token 都要常驻显存 是部署长上下文模型最贵的部分
费用（按 token 计费） 0.001 元级 同等问题长上下文贵出数量级 商业系统必须控制输入长度
响应质量 稳 中段信息容易丢、容易分心 长 ≠ 强

课程里给的一组参考值："同样问题，32K 上下文比 4K 上下文慢约 3~8 倍、贵约 8~16 倍"。 真实数字依硬件和模型变，但量级一致——这就是为什么所有 Agent 框架都会做上下文压缩。

常见压缩策略

  • 滚动摘要：每 N 轮把历史总结成一段，丢原始对话
  • 按需检索：用向量库只取当下问题相关的几段历史，不全塞
  • 工具结果截断：把超长的工具返回值裁剪/摘要后再放回上下文
  • 分层上下文：系统级、任务级、对话级分开管理，按需加载

四、RAG：把"上下文"主动喂进去

RAG（Retrieval-Augmented Generation） 当前是大模型应用里最常见的"上下文注入"手段。 思路非常简单：模型不用全记住知识库，而是每次提问前先把相关片段检索出来，临时拼进上下文。

用户提问
查询改写（可选）
向量检索 / 关键词检索
知识库命中 TopK 片段
拼接到 Prompt
大模型基于片段回答

RAG 关键点（课程作业考察范围）

  • 检索质量比模型大小更重要：检索回来一堆噪声，再大的模型也救不回来
  • 片段拼接顺序：相关片段放在用户问题之前通常更有效
  • 标注出处：让模型回答时引用片段来源，降低幻觉率
  • 分块策略：太碎丢失语义、太长带噪声；课程推荐按章节/标题切分
  • 检索 ≠ 答对：检索覆盖不等于模型引用，必要时加"看引用再答"的强提示
课程上老师对 RAG 的原话："RAG 不是万能解药。它能让模型看见资料， 但不能保证它看懂资料，也不能保证它只用资料。"——这是 Agent 工程化最常见的踩坑来源。

五、上下文怎么影响 Agent 运行（呼应 Agent 笔记）

把上下文和 Agent 联系起来：上下文是 Agent 的"工作记忆"。它直接影响 Agent 的四件事——

Agent 行为上下文作用常见故障
规划模块 计划必须放在上下文里，否则 Agent 会重复生成计划 Agent 反复重新规划、陷入死循环
工具调用 工具列表 + 工具返回值都拼进上下文 工具太多挤掉系统提示，模型忘记工具规范
记忆模块 长期记忆通过检索后注入上下文 检索回错片段 → 模型依据错的"回忆"行动
反思校验 上次结论必须留在上下文才能比较 忘了上次结果，重复犯同一个错

六、容易混淆的点 / 使用边界

易混说法我目前的理解
"上下文越长越聪明" 不一定。Lost-in-the-Middle + 算力爆炸 + 错误信息污染，反而更笨
"RAG = 搜索 + ChatGPT" 不只搜索。检索质量、切块、注入位置、重排序都是工程活
"上下文窗口是模型的"内存" 不是。是这次请求的输入上限，请求结束显存释放
"把所有文档塞进上下文就行" 塞进去 ≠ 模型读进去；超长还会显著抬升成本与延迟
"上下文越多越准" "准"还取决于相关性。噪声上下文比短上下文更糟

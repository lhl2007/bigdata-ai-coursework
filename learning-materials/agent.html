Agent 智能体 —— 课程作业笔记

大数据与人工智能课程作业个人理解 · 仅代表本人当前认知，欢迎指正

Agent（智能体） 简单说就是"让大模型自己动手干活"的程序。它不是只会聊天的机器人， 而是会观察任务、规划步骤、调用外部工具、检查结果，必要时再来一轮的自主行动者。

课程里把它和"普通大模型对话"区分开：本课讲的 Agent 强调两件事—— 能拆任务 能动工具， 普通问答式 LLM 用法没有这两条。

一、Agent 与"普通 LLM 调用"的差别

维度普通 LLM 调用Agent
输入 用户问一次，模型答一次 用户给目标，Agent 自己拆步
工具 不调用外部工具，纯生成文本 会调 API、读写文件、查库、执行代码
中间过程 一次推理结束 多轮：观察 → 思考 → 行动 → 再观察
结果正确性 出错也只是输出错了 可自检、可回滚、可重新尝试
典型场景 问答、翻译、改写 自动化运维、数据分析 Agent、编程助手

二、Agent 的四大组件

课程里讲一个完整 Agent 通常由下面四个模块组成，缺一不可。

① 记忆模块 Memory

Agent 不是一次性调用，它要"记得"之前发生了什么。记忆通常分两类：

  • 短期记忆：当前这一轮会话内放在上下文里的对话历史、工具返回值
  • 长期记忆：用向量数据库或文件存下来的历史经验，下次任务可以检索出来再用
课堂上老师演示过一个坑：让 Agent 跑 50 步任务，前 30 步的结论必须真的写进记忆， 否则最后 20 步模型会"忘了"前面的设定，做出前后矛盾的决策。

② 规划模块 Planning

把"用户给的大目标"拆成"Agent 能一步步执行的小任务"。课程上提到了两类主流做法：

模式思路适合
ReAct
（Reason + Act）		 每一步都先想"我下一步该做什么"，再决定调什么工具，再观察结果 调试透明、问题路径不清晰的任务
Plan-and-Execute 先一次性把完整计划生成出来，再按步骤执行；中途失败再回过来修计划 目标明确、可以提前拆解的任务

老师原话："规划不是越细越好，规划太细反而会僵。"实际项目里我看到的大多 Agent 都会混合用。

③ 工具调用 Tool Use

Agent 真正的能力来自工具——大模型自己不能联网、不能读写你电脑上的文件、不能查数据库。 工具调用就是让模型输出"我想调哪个工具、参数是什么"，由 Agent 框架去真正执行并把结果拿回来。

  • Function Calling：模型按 JSON Schema 输出结构化调用请求
  • MCP（Model Context Protocol）：把工具做成标准协议，跨框架/跨模型复用
  • 代码解释器：让 Agent 跑一段生成的代码，把运行结果当观察
工具设计的关键经验：工具参数越明确、报错信息越详细，Agent 越不容易乱调。 课程上举的反例是给一个"万能工具"参数叫 action: string， 结果 Agent 每次都不知道该传什么。

④ 反思校验 Reflection

Agent 跑完一步不能直接相信结果，要回头看"我这一步是不是对的"。反思至少要回答：

  • 输出格式对不对？（比如该返回 JSON 但返回了自然语言）
  • 结果内容是否前后矛盾？
  • 是否触发了工具失败、是否要换路径？
  • 如果连反思都不对——触发"卡死检测"，主动停下来

课堂上一个形象说法：Agent 没有反思就像闭着眼干活的工人，工具返回啥就信啥， 错了也接着错下去。反思模块就是把"睁眼检查"这一步显式做出来。

三、四大组件怎么串起来

用户目标
规划模块：拆成 N 步
当前步骤 i
记忆检索（把相关历史拿出来）
大模型生成行动
工具调用模块：执行工具
观察 / 工具返回值
反思校验：够不够好？
通过 → 进入下一步 i+1

整条链路循环跑，直到规划里的所有步骤都通过反思，或触发"放弃"分支。 课程作业里如果要画流程图，记得把记忆检索也画上—— 没有记忆检索就只能做"无状态任务"，那不叫 Agent，叫脚本。

四、真实应用场景（课程作业里能举的例子）

场景Agent 怎么做的用到的组件
代码助手（Cursor / Copilot Agent 模式） 先理解任务→拆成"读文件→改文件→跑测试→修问题"→循环 规划 + 工具 + 反思
数据分析助手 自然语言提问 → 自动生成 SQL → 查库 → 解释结果 → 必要时画图 工具调用 + 反思（SQL 错了重试）
自动化运维 / RPA 升级版 收到告警 → 查日志 → 定位问题 → 执行修复脚本 → 验证恢复 记忆（历史告警）+ 规划 + 工具
研究型 Agent（深度搜索） 多轮搜索 → 拼接片段 → 总结 → 引用检查 长期记忆 + 反思（避免幻觉引用）

五、容易混淆的点 / 使用边界

易混说法我目前的理解
"Agent = 高级一点的 ChatGPT" 不对。区别在是否能动工具、是否能拆步循环，缺这两条就不算 Agent
"Agent 组件越多越好" 不是。组件对应真实需求；硬塞反思/记忆到简单任务上只会拖慢且不稳
"用了 Function Calling 就是 Agent" 还得看有没有循环和目标驱动。一锤子请求不叫 Agent
"Agent 自己能保证正确" 不能。反思只降低错误率，不能消除；关键业务仍需人在回路
"记忆越多越好" 不是。脏记忆会污染决策（详见 LLM Context 笔记）

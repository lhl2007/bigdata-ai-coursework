Agent / 大模型上下文 / Skill —— 三者关系

课程作业个人理解 · 仅代表本人当前认知，欢迎指正

最近接触"Agent"、"上下文"、"Skill"这三个词经常同时出现，看似都是大模型应用的同义词， 实际上各自承担的角色并不重叠。这份笔记按我个人理解把它们拆开来讲，重点回答两件事：

  • 大模型上下文是怎么影响 Agent 运行的？
  • Skill 如何沉淀可复用的任务知识？

一、三个概念分别是什么

概念 我的一句话定义 类比
Agent 由大模型驱动、能调用工具、自主分步完成任务的程序 有手有脚的员工
大模型上下文 本轮对话里模型能"看见"的所有信息（系统提示、对话历史、工具返回值） 员工此刻办公桌上摆的资料
Skill 预先写好的、可被加载进上下文的"任务知识包"（提示词模板、最佳实践、领域经验） 员工桌上的岗位 SOP 手册

二、整体关系图

可以这样记：Skill 是"放在抽屉里的"知识，Context 是"摆在桌上"的当前材料，Agent 是"动手干活"的那个角色。

三、重点一：大模型上下文如何影响 Agent 的运行

Agent 每走一步都要把"目前桌上有啥"完整喂给大模型，这个"桌上的全部材料"就是上下文窗口。 我目前看到的几个具体影响：

3.1 上下文决定了 Agent "知不知道"

  • 用户初始需求没写清的细节 → 必须在上下文里写明，模型才能处理
  • 工具调用的返回值 → 必须拼回上下文，下一步模型才知道发生了什么
  • 之前的决策 → 上下文不携带，Agent 就会"失忆"地重复犯同一个错

3.2 上下文长度是硬约束

  • 几乎所有大模型都有上下文上限（几千到几十万个 token）
  • Agent 跑得越久，对话越长，历史被挤出去，模型表现就会"突然变笨"
  • 所以 Agent 通常要做上下文管理：截断、压缩、把不重要的丢出去，只留当下决策必需的信息

3.3 上下文污染会让 Agent 卡死

真实坑：工具返回的错误信息、用户的中途打断、上一轮的多余猜测，都可能被反复带进上下文， 让模型陷入"在错的信息上反复推理"的循环。这是 Agent 工程里非常常见的稳定性问题。
现象通常原因常见对策
模型反复追问同一个问题上轮回答没被携带回来把回答显式追加到上下文
模型陷入错误路径错误信息被反复喂入触发失败后清理对应上下文
长任务后期变笨上下文超长，关键信息被截掉定期做摘要压缩、丢弃过期片段
用户改主意后模型还在按旧计划做新指令没覆盖旧上下文重置上下文或追加显式"忽略之前"

四、重点二：Skill 如何沉淀可复用任务知识

同一个任务，下次还要做——这是 Skill 存在的根本理由。我理解的沉淀方式有三层：

4.1 Skill 的最小形态：一段提示词

例：让模型写 SQL 时附带"先用 EXPLAIN 检查执行计划、再决定是否建索引"——这就是一个微型 Skill。

4.2 Skill 的工程形态：可被加载的模块

工程上 Skill 通常是一个目录（或一个对象），里面包含：

  • SKILL.md：描述这个 Skill 是干什么的、什么时候用、怎么用
  • references/：详细参考资料、领域知识
  • 必要时附带脚本或资源

Agent 在需要时把它的"系统说明"或"参考材料"临时注入到当前上下文里， 任务结束就把这段上下文丢弃。这样 Skill 不会污染 Agent 的默认行为，又能在需要时被检索到。

4.3 Skill 沉淀的关键好处

沉淀前沉淀后
每次任务都要重新告诉模型怎么做 Agent 自动加载 Skill，按已有流程跑
经验只存在某次对话里 经验写进 Skill，下次还能用
不同人/不同项目重复发明轮子 团队共享一份 Skill，行为一致
提示词越堆越长，挤占上下文 按需加载，不用时不占窗口

六、容易混淆的点

易混说法我目前的理解
"Skill 就是一段 Prompt" 形态上没错，但不只 Prompt。Skill 还可以包含工作流、参考资料、校验脚本
"上下文越长 Agent 越聪明" 不一定。超长上下文里"关键信息被淹没"反而更笨；做摘要、按需加载才是关键
"Agent 越多越好" 单 Agent 也能完成多数任务，多 Agent 适合角色清晰、可拆解的场景；不是越大越强
"Skill 一旦写好就万能" Skill 也需要维护。模型/工具变了，Skill 可能失效
